## 지금까지 진행된 변경 (미커밋, `generator_v2.py`)

기존에는 832×1216 해상도로 렌더링하다 M4 16GB에서 스왑(step당 8~40s로 불안정)이
발생해 `attention_slicing` + `vae.enable_slicing()`을 켰음(직전 커밋 `429d0eaf`).
그런데 슬라이싱을 켠 상태에서 **검은/단색 프레임(NaN)** 이 간헐적으로 재현되기
시작함 — MPS+fp16 조합에서 슬라이싱이 수치 불안정을 악화시키는 것으로 추정.
`vae.to(torch.float32)` 업캐스트도 시도했으나 정상이던 것까지 깨져서 폐기.

**최종 결론 및 현재 코드 상태:**
- 해상도를 **768×768(정사각)** 로 낮춤 — 앱에서 실제 표시 크기가 최대
  ~350×192(SRS 카드) / 64×64(썸네일)라 832×1216은 과했음. 메모리 부담이
  이것만으로 42% 줄어 슬라이싱 없이도 스왑을 피함.
- `attention_slicing` / `vae.enable_slicing()` **제거**.
- 그래도 드물게 나올 수 있는 검은 프레임을 `is_degenerate_frame()`(픽셀
  표준편차 < 1.0)로 감지해 최대 3회 자동 재시도, 3회 모두 실패하면 해당
  단어를 건너뛰고 로그만 남김.
- 저장 포맷을 **PNG → JPEG**(quality=88)로 변경. PNG는 이 화풍에서 장당
  ~900KB라 8,424장이면 앱 번들이 7GB+가 됨. 파일명도 `.png` → `.jpg`.
- 테스트 결과: `n4_気_신경.jpg` 86KB, `n4_それで_그래서.jpg` 115KB — 용량도
  기대대로 크게 감소.

## 추후 계획

1. **커밋 여부 결정 대기 중** — 위 변경사항(`generator_v2.py`)과 재생성된
   테스트 이미지 2장이 아직 커밋되지 않음. 사용자 확인 후 커밋 예정.
2. 소수 단어 검증 완료 → 다음은 더 큰 배치(예: `--count 20~50`)로 안정성
   재확인 후 N4 전체(→ 이후 N1~N5 전체 8,424개) 본 배치 실행.
3. `assets/images/words_v2/`에 생성된 이미지를 앱에 실제로 연결하는 작업은
   **아직 미착수**. README에 명시된 대로, id 기반이 아니라
   `레벨_일본어_한국어` 조합 파일명이므로 `wordImages.ts`(또는 해당 매칭
   로직)를 이 조합 기준으로 새로 작성해야 함.
4. `data/jlpt_catbatches_n4/`, `data/jlpt_categories_n4/`(각 batch_00~04.json,
   untracked) — N4 단어를 5개 배치로 나눠 카테고리 분류(concrete_nouns 등)한
   중간 산출물로 보임. `word_categories.json`을 만드는 데 쓰인 스크래치
   데이터인지, 아직 반영 안 된 재분류 작업인지 확인 필요 — 다음 세션에서
   목적 파악 후 커밋하거나 정리.

## 문제가 될 가능성이 있는 부분

1. **커널 패닉 재발 가능성** — 이번엔 2장(총 ~3분)만 테스트해 재현되지
   않았을 뿐, 근본 원인(SoC 레벨 abort)이 완전히 규명된 건 아님. N4 전체
   (수백 장) 같은 장시간 고부하 배치 실행 시 다시 발생할 수 있음. 배치를
   작게 나눠 돌리거나, 실행 중 발열/메모리 상태를 주시할 필요가 있음.
2. **`.png` → `.jpg` 확장자 변경과 idempotency 체크** — `main()`의
   "이미 생성된 이미지는 건너뛴다" 로직(`--overwrite` 미지정 시)이
   `output_path_for()`가 반환하는 **새 확장자(.jpg)** 기준으로 파일 존재
   여부를 검사함. 지금은 `assets/images/words_v2/`가 사실상 비어 있어
   문제가 없지만, 만약 과거에 `.png`로 생성해둔 자산이 쌓인 뒤 이 코드로
   돌리면 전부 "없음"으로 인식해 **중복 재생성**(GPU 시간 낭비)이 발생함.
   본 배치 실행 전에 한 번 더 점검 필요.
3. **앱 쪽 미연동** — `wordImages.ts` 등에서 `words_v2` 자산을 참조하는
   코드가 아직 없음(grep 결과 0건). 이미지가 다 생성돼도 앱에 자동으로
   반영되지 않으므로, 매칭 로직 작성을 누락하면 "이미지는 만들었는데 앱에
   안 보임" 상태로 방치될 수 있음.
4. **검은 프레임 3회 재시도 후 조용히 스킵** — 대량 배치 실행 시 3회 모두
   실패한 단어는 로그 한 줄(`❌ ... 건너뜀`)만 남기고 지나감. 수천 단어를
   한 번에 돌리면 이 로그를 놓치기 쉬워, 실행 후 반드시 "몇 개가
   스킵됐는지" 별도로 집계/확인하는 절차가 필요함.
5. **Gemini API 레이트리밋** — 큐레이션 태그가 없는 단어는 매번 Gemini
   호출(`get_danbooru_tags`) 후 `sleep(2)`만 두고 있음. 대량 배치에서는
   여전히 레이트리밋에 걸릴 수 있음(현재 3회 재시도 로직은 있음).
6. **워킹 트리에 무관한 변경이 섞여 있음** — 같은 저장소 루트에 haru-nihonggo와
   전혀 무관해 보이는 Vite/Three.js 관련 변경(`index.html`, `package.json`,
   `src/main.jsx`, `Michelle.glb`, `kenney_chars/`, `test-fbx.js` 등, 모두
   untracked/modified)이 함께 존재함. `generator_v2.py` 변경을 커밋할 때
   실수로 이 무관한 파일들까지 같이 스테이징되지 않도록 `git add`를 파일
   단위로 명시할 것.
